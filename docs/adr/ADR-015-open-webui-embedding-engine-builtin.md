# ADR-015 — Open WebUI Embedding Engine: Switch from Ollama to Built-in

**Status:** Accepted  
**Date:** 2026-05-26

## Context

Open WebUI (`chat.kostikidis.net`, `ai` namespace) has a built-in RAG / knowledge base system. Its embedding engine was configured to use Ollama:

| Setting | Configured value |
|---------|-----------------|
| Embedding Model Engine | Ollama |
| Ollama URL | `http://ollama.ai.svc.cluster.local:11434` |
| Embedding Model | `sentence-transformers/all-MiniLM-L6-v2` |

Two faults made this configuration silently broken:

**Fault 1 — Ollama deployment scaled to 0 (ADR-017).**  
The in-cluster CPU Ollama Deployment (`ollama.ai.svc.cluster.local`) was scaled to 0 replicas as a consequence of the LiteLLM resilience work in ADR-017. Its fans-at-full-speed behaviour during GPU fallback made it unsuitable as a hot standby. With the Deployment at 0 replicas, every embedding request fails. Failures are silent — Open WebUI does not surface them as errors in the UI.

**Fault 2 — Invalid model identifier.**  
`sentence-transformers/all-MiniLM-L6-v2` is a HuggingFace repository path. Ollama does not recognise it. The correct Ollama identifier for MiniLM-L6 is `all-minilm`. The configuration was never functional under Ollama even before the scale-to-0.

The practical effect: the knowledge base (including the Dr. Ali Adnan exam collection — see ADR-016) could not index or retrieve documents. The feature appeared to work but embeddings were never generated.

## Decision

Switch the Open WebUI embedding engine to **Default** (Open WebUI's built-in sentence-transformers runner):

| Setting | New value |
|---------|----------|
| Embedding Model Engine | Default (built-in) |
| Embedding Model | `sentence-transformers/all-MiniLM-L6-v2` |

In Default mode, Open WebUI runs the model in-process via its own Python sentence-transformers runtime. The model (`all-MiniLM-L6-v2`, 384-dimensional embeddings) is identical to the intended Ollama configuration — it was just never reachable through Ollama. The embedding backend is now self-contained within the Open WebUI pod. No external Ollama instance is required.

After the engine switch, the knowledge base must be reindexed:  
**Admin → Settings → Documents → Reindex** (or delete and re-upload collections).

## Revert Path

This is the primary reason this ADR exists. To revert to Ollama-backed embeddings:

1. **Restore the in-cluster Ollama Deployment to 1 replica** (if CPU inference is acceptable again):
   ```
   kubectl scale deployment ollama -n ai --replicas=1
   ```
   Alternatively, point at the GPU-side Ollama — see step 2.

2. **Open WebUI Admin → Settings → Documents**, set:
   - Embedding Model Engine: `Ollama`
   - Ollama URL: `http://ollama.ai.svc.cluster.local:11434`  
     (or `http://ollama-gpu.ai.svc.cluster.local:11434` to use the GPU LXC instead)
   - Embedding Model: `all-minilm`  
     (this is the correct Ollama identifier — **not** the HuggingFace path `sentence-transformers/all-MiniLM-L6-v2`)

3. **Reindex** the knowledge base.

Note: if switching from Default to Ollama, embedding dimensions remain 384-dim (`all-minilm` and `all-MiniLM-L6-v2` are the same model). No reindex is strictly required for dimension compatibility, but a reindex is recommended because the embedding vectors will have been generated by a different runtime and numeric equivalence is not guaranteed.

## Alternatives Considered

- **Fix the Ollama configuration (correct model name + scale Deployment back to 1)** — rejected for now. The CPU Ollama on k3s-prg-b3 was scaled to 0 because it hammers the cluster node during LiteLLM fallback. Scaling it back to 1 for embedding traffic reintroduces that risk. ADR-017 explicitly moved CPU inference off cluster nodes; embedding requests should follow the same principle.

- **Route embedding requests to `ollama-gpu` instead** — viable but deferred. See the future migration note below. GPU Ollama carries models designed for inference, not embeddings; pulling an embedding model (`all-minilm` or `nomic-embed-text`) on LXC 110 is a separate action that requires testing.

- **Deploy a dedicated embedding service (FastEmbed, Infinity, etc.)** — over-engineered for current volume. Open WebUI's built-in runner is sufficient. A dedicated service would be appropriate at higher query volume or if multiple apps needed to share embeddings.

## Future Migration (not decided)

Post-travel: consider migrating to `nomic-embed-text` via `ollama-gpu` (LXC 110, `192.168.1.224`) for higher embedding quality. `nomic-embed-text` produces 768-dimensional embeddings vs. 384-dim for MiniLM — roughly double the representational capacity for long-form documents such as the study notes and PDFs currently in the knowledge base.

To execute: pull `nomic-embed-text` on LXC 110, point Open WebUI embedding engine to `ollama-gpu`, update model name, and reindex. Switching embedding dimensions requires a full reindex — there is no in-place upgrade path.

This is a one-way door at the data layer: once reindexed at 768-dim, reverting to 384-dim requires another full reindex.

## Consequences

**Wins:**

- Knowledge base embeddings work immediately. No Deployment scaling, no external dependency.
- Removes the broken HuggingFace-path model name from the configuration permanently.
- Self-contained: Open WebUI pod carries everything it needs for embeddings. No Ollama pod required.
- Consistent with ADR-017's principle of keeping cluster nodes out of inference paths.

**Costs:**

- Embedding runs in the Open WebUI pod's CPU budget. For the current volume (one knowledge collection, ~2 GB of PDFs for Dr. Ali's exam), this is acceptable. At higher volume or with concurrent users, this could become a bottleneck.
- After the engine switch, existing knowledge base entries are stale. A full reindex is required before the knowledge base returns useful results.
- The built-in runner downloads the model on first start if not already cached. First embedding request after a pod restart may be slow until the model is warm.

**Broken configuration removed:**

The previous configuration (Ollama engine + HuggingFace model path) was never functional. There is no working state to preserve or degrade from. This change moves from a silently broken state to a working one.
