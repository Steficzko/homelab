# Longhorn v1.13.0

## Install method: kubectl apply (NOT helm)

Longhorn ships a single all-in-one manifest. It was applied directly — no Helm release, no release secret, no `helm upgrade` lifecycle.

```bash
kubectl apply -f https://raw.githubusercontent.com/longhorn/longhorn/v1.13.0/deploy/longhorn.yaml
```

After the base install, apply custom settings:

```bash
# from repo root:
kubectl apply -f kubernetes/infrastructure/longhorn/default-setting.yaml
```

> Re-apply after every Longhorn version upgrade — the base manifest resets this ConfigMap to empty.

## Why kubectl apply, not helm

The Longhorn project publishes `longhorn.yaml` as the primary install method. Using it means:
- No Helm release Secret in-cluster
- No `helm upgrade` — to upgrade, apply the new version's longhorn.yaml
- No `helm rollback` — rollback means applying the old version's longhorn.yaml

## Custom settings (default-setting.yaml)

| Setting | Value | Reason |
|---|---|---|
| `priority-class` | `longhorn-critical` | Prevents eviction under node memory pressure |
| `disable-revision-counter` | `true` | Reduces write IOPS on volumes |

## StorageClass (auto-generated by Longhorn)

- Name: `longhorn` (cluster default)
- `numberOfReplicas: 3`
- `fsType: ext4`
- `reclaimPolicy: Retain` (since 2026-10-24, STOR-48: a deleted PVC or an Argo prune must not destroy data).
  Set in the `longhorn-storageclass` ConfigMap, which Longhorn turns into the StorageClass. **The upstream
  `longhorn.yaml` ships `Delete`, so every Longhorn upgrade resets it:** after `kubectl apply` of a new
  version, re-run
  `kubectl -n longhorn-system get cm longhorn-storageclass -o json | jq '.data["storageclass.yaml"] |= sub("reclaimPolicy: \"Delete\""; "reclaimPolicy: \"Retain\"")' | kubectl apply -f -`
  and check `kubectl get sc longhorn`. Existing PVs were patched to `Retain` one by one; a deleted PVC now
  leaves a `Released` PV and its Longhorn volume, to be removed by hand once the data is not needed.
- `dataLocality: disabled`
